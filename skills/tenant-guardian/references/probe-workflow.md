# Synthetic GET probe workflow

Prepare two isolated fixture tenants and two real but synthetic test identities whose memberships are known. Seed opaque, distinct markers in stored response data using the application test harness, not the request path or credential. The runner creates no accounts or data. Confirm every configured GET is safe to invoke and review its handler for side effects.

The plan declares an exact origin, environment (local/test/staging), actor labels, token environment-variable names, resource owner labels, safe relative paths and markers. Use no real customer records. Token values must already be present in the operator's process environment; do not paste values into commands, plan files, prompts or assessment records. The runner does not read `.env` or credential files.

Run --dry-run first. It validates the plan without reading credentials or contacting the origin. Active probing requires --allow-network, --synthetic-only and an exact --allow-origin match. HTTP is supported only for explicitly selected localhost/loopback fixtures; staging requires HTTPS. Only two distinct synthetic actors and up to twenty known resources are supported. No writes, enumeration, redirects, retries, cookies or environment proxies are used. Each request has a bounded timeout and response-size limit; total duration depends on the number of configured resources.

The runner first sends an own-tenant GET for every resource. All must return 200 with the correct seeded marker, no foreign seeded marker, no truncation and no transport error. If any baseline fails, cross-tenant requests are skipped. Baseline foreign-marker leakage remains an observed failure. This conservative rule can produce inconclusive cases when part of the fixture is broken.

For cross-tenant reads, any known foreign marker in the retained response prefix produces leak_observed, regardless of status. A nontruncated, clean 403/404 after working positives produces denied for that exact configured GET. 401, 3xx, timeouts, server errors, empty 200s and truncation without a detected foreign marker are inconclusive. Markers that are escaped, transformed, encrypted or returned beyond the limit may be missed; nondetection never establishes safe disclosure. Other response fields and metadata can leak even when marker tests deny access, so review beyond the marker oracle.

Only labels, status codes, marker-presence booleans, request counts, truncation/error flags, a canonical plan SHA256 and hashes of retained response bytes are persisted. No tokens, bodies, marker strings or request paths are written. Compare the plan hash with the access-controlled approved plan when reviewing results; hashing does not prove the plan's truth or authorization. Hashes and labels may still reveal metadata; treat results as sensitive. No assessment statuses are changed. A responsible reviewer must link the result to relevant objective and scope.

For writes, search/list/aggregation, storage signing, jobs, restores, websockets, pooled DB connections and AI tools, use the app-specific regression plan and authorized integration tests. This HTTP runner cannot verify those boundaries.
